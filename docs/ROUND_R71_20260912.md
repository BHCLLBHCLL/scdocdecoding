## 2. 三条实测教训

1. **ctypes 调内存计数器要两件套**：伪句柄 `(HANDLE)-1` 需要显式 `restype`（否则被截成 32 位），
   且查询需要 `argtypes`（否则**返回 0 而不报错**）。修好之前，代码静默回退到 tracemalloc，
   把 **0.2 MB 的 Python 峰值当成进程峰值**报了出去（真实是 149.5 MB）。
2. **测量工具不得改变被测对象**：`measure()` 里 `tracemalloc.start()` 后不停，等于给整个进程装上分配跟踪器——
   同进程内**下一个**测试慢了 **6×**（官方样例加载 4 s → 26 s），并直接把既有 `test_library_load_budget` 打红。
   现在 tracing 的生命周期被 `measure()` 严格包住（读完峰值立即 `stop()`），`python_peak_mb()` 也不再自行启动跟踪器。
3. **负载敏感的预算要取"空载最好值"**：同一条样例加载，并发跑套件时 26.4 s、单独空载 4 s。
   `test_library_load_budget` 改为**两次取较快值**，并在测试 docstring 里写明这两个实测数字。

## 3. 新增纪律

85. **测量工具不得改变被测对象**。全局副作用（tracing、profiler、日志级别、缓存）必须在测完**立即解除**，
    并且要有一条"测量前后同一基准不变"的验证；R71 实测：漏掉 `stop()` 让同进程后续测试慢 6×，
    把一条既有预算测试直接打红——**测坏别人**比测不准更隐蔽。
